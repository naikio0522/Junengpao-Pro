# 0.x 强制更新策略

从 v0.1.9 开始，Windows 和 macOS 客户端在启动时读取各自的 `update-channel-0/windows.json` 或 `macos.json`。清单字段 `minimumSupportedVersion` 指定当前平台允许继续使用的最低稳定 `0.x.y` 版本。只有本机版本低于该字段时才显示更新门槛；字段缺省时仍按普通可选更新处理。每个平台发布新的正式安装包时，工作流默认将该平台最低支持版本设为新安装包版本；没有新安装包的平台继续保留原有清单。

清单中的最低版本必须是规范的稳定 `0.x.y`，且不能高于该清单的安装包版本。客户端仍只接受本仓库对应 `v0.x.y` Release 的平台安装包和有效 SHA-256。Windows 安装包在启动前再次校验任务状态；主混剪、独立去重、去水印、链接下载、压测、预检和 SRT 导出中只要有任务正在等待或运行，或者任务状态无法确认，就不启动安装向导。启动门槛会等待这些任务完成，不会自动停止它们。macOS 只打开已校验的 DMG，用户仍需手动完成安装。

## 发布和调整

1. 发布 v0.1.9 或后续正式 `v0.x.y` Release，并附上对应平台安装包。正常发布会自动把有新安装包的平台最低支持版本设为该安装包版本；例如只附 Windows 安装包时，macOS 清单保持原样。
2. 若需紧急放宽策略，在 GitHub Actions 中手动运行 `Publish 巨能跑pro版 0.x update channel`。`release_tag` 填当前平台通道所指向、包含该平台安装包的已发布标签，例如 `v0.1.9`。按平台填写 `minimum_windows_version` 或 `minimum_macos_version`：可填较低的稳定 `0.x.y`，或填 `none` 撤销该平台的强制更新；不调整的平台留空。两个平台的最新安装包分属不同 Release 时，分别运行工作流。
3. 工作流会验证已有通道与目标 Release，允许在同一安装包版本下调整最低版本，不允许用旧 Release 把平台通道降级。手动重发同一版本且输入留空时会保留已有策略；下一次正式发布新安装包时，默认策略又会收紧到新版本。
4. 核对重新上传的 `windows.json`、`macos.json`：`version` 是该平台实际可下载安装包版本；除显式使用 `none` 的平台外，`minimumSupportedVersion` 不高于 `version`。

v0.1.8 及更早已发布的二进制不会因服务器后来增加字段而获得强制更新能力；它们仍按原有逻辑处理更新。首次迁移旧仓库地址的客户端仍需手动安装指向本仓库的版本。更新通道网络超时、HTTP 错误或清单无效时，尚无有效强制更新缓存的客户端会进入软件并提示稍后重试。此前已在线确认必须更新的客户端会沿用本机保存且重新校验过的策略，继续显示更新门槛与官方发布页入口；可在联网后重试，或手动安装已获取的官方最新版。在线取得不再要求更新的有效清单时会清除缓存。缓存只用于当前安装版本，不会锁住已升级的版本。
